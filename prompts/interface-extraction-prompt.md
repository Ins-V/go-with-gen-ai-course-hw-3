## Мій промпт

### РОЛЬ

Ти — досвідчений Go-розробник (10+ років), що спеціалізується на чистій
архітектурі та ідіоматичному Go. Ти сповідуєш правило спільноти Go:

### КОНТЕКСТ

Маю пакет `orders` у Go-модулі `example.com/lesson03`. Сервіс напряму залежить від
`*sql.DB`, через що його неможливо протестувати без реальної бази:

```go
package orders

import "database/sql"

type OrderService struct {
    db *sql.DB
}

func NewOrderService(db *sql.DB) *OrderService {
    return &OrderService{db: db}
}

func (s *OrderService) PlaceOrder(orderID string, amount float64) error {
    _, err := s.db.Exec(
        "INSERT INTO orders (id, amount) VALUES (?, ?)",
        orderID, amount,
    )
    return err
}
```

Єдина операція з БД, яка реально потрібна сервісу, — виконання
INSERT-запиту. Решта можливостей `*sql.DB` сервісом не використовується.

### ЗАВДАННЯ

1. Згенеруй мінімальний інтерфейс `OrderStore`. Він має містити
   рівно стільки методів, скільки реально викликає `OrderService`.
   Проаналізуй код і доведи (одним реченням у коментарі),
   чому кожен метод там потрібен. Сигнатура методу має бути такою:
   `Exec(query string, args ...any) error`.
2. Перепиши `OrderService` на dependency injection через
   конструктор. Поле структури — тип інтерфейсу `OrderStore`
   (не вказівник на інтерфейс, не конкретний тип). Конструктор
   `NewOrderService(store OrderStore) *OrderService` приймає залежність
   ззовні; сервіс не створює з'єднання з БД сам і не імпортує
   `database/sql`. Метод `PlaceOrder(orderID string, amount float64)
   error` викликає `store.Exec` із SQL-запитом і аргументами
   `orderID`, `amount`, повертає помилку як є (обгортай через
   `fmt.Errorf("...: %w", err)` лише якщо додаєш контекст) або `nil`.
3. Згенеруй мок-реалізацію `OrderStore` для тестів без реальної БД.
   Це має бути ручний фейк у стилі стандартної бібліотеки.
   Мок має:
   - лічильник викликів `Exec`;
   - збережені останні `query` та `args` — щоб тест міг перевірити,
     що передано саме `orderID` та `amount`;
   - поле-помилку, яку `Exec` повертає, щоб перевірити шлях із
     помилкою;
   - перевірку відповідності інтерфейсу на етапі компіляції:
     `var _ OrderStore = (*mockOrderStore)(nil)`.
   Додай два табличних (або два окремі) тести на `go test`: успішна
   вставка та поширення помилки від сховища.

### ОБМЕЖЕННЯ

- Мова коду — Go 1.22, лише стандартна бібліотека (`errors`, `fmt`,
  `testing`); жодних сторонніх пакетів.
- Інтерфейс — мінімальний. Не додавай методи про запас. Якщо вважаєш, що
  якийсь метод потрібен, або доведи це викликом у коді, або не додавай.
- Інтерфейс оголошується в пакеті-споживачі `orders`, поруч із
  `OrderService`, а не в пакеті з реалізацією БД.
- Код має проходити `gofmt -l .` і `go vet ./...` без зауважень.
- Іменування — ідіоматичне Go: `MixedCaps`, без префікса `I` в назві інтерфейсу.
- Кожен експортований тип і функція — з doc-коментарем, що починається
  з імені сутності. Коментарі англійською.
- Помилки не ковтати: `PlaceOrder` зобов'язаний повертати помилку
  від `Exec`.
- Мок живе у файлі `_test.go`, тому неекспортований і не потрапляє у
  прод-збірку.
- Ніяких фреймворків DI, глобальних змінних, `init()`, синглтонів і
  panic.
